# Scoop manifest

`bucket/storyforge.json` is generated by `scripts/packaging/update-manifests.ts`
from the release assets — never edit it here.

## Install

```powershell
scoop bucket add lovelesscodes https://github.com/LovelessCodes/scoop-bucket
scoop install storyforge
```

## Two sources

The generator prefers `Story.Forge_<version>_x64-portable.zip` and falls back to
the NSIS installer when a release has no portable build:

| Source         | Manifest shape                                             |
| -------------- | ---------------------------------------------------------- |
| portable zip   | `url` → `..._x64-portable.zip`, shortcut `Story Forge.exe` |
| NSIS installer | `url` → `..._x64-setup.exe#/dl.7z`, `post_install` cleanup |

`2.0.11` (and everything before it) uses the installer: Tauri's NSIS setup is a
7-Zip-readable archive, so Scoop unpacks it and `post_install` removes the
`$PLUGINSDIR` / `$TEMP` helpers. From the first release after the portable zip
lands, the manifest switches to the plain zip.

Why a portable zip is better: Tauri embeds the frontend and `tauri.conf.json`
declares no sidecar resources, so the release exe is already self-contained. A
zip of it means Scoop manages exactly one file, with no installer layout to rely
on and nothing to clean up. The only requirement is the WebView2 runtime, which
ships with Windows 10/11 and is what the installer would have bootstrapped.

## One-time setup (human)

The bucket repository `LovelessCodes/scoop-bucket` exists and is current. The
`scoop` job in `.github/workflows/distribute.yml` keeps it that way using the
same `PACKAGING_TOKEN` PAT as the Homebrew tap (`Contents: read and write` on
this repository) — see `packaging/homebrew/README.md`.

Pushing by hand, if the token is not set yet:

```sh
bun scripts/packaging/update-manifests.ts --only scoop
git clone git@github.com:LovelessCodes/scoop-bucket.git
cp packaging/scoop/bucket/storyforge.json scoop-bucket/bucket/
cd scoop-bucket && git add bucket && git commit -m "storyforge: update to 2.0.11" && git push
```

## Update flow

`checkver` reads the newest GitHub release tag (`storyforge-v2.0.11`) and
`autoupdate` rewrites the URL from it, so the manifest keeps working even if the
distribution workflow is skipped — Scoop users can always pick up a new release,
and the pushed manifest normally arrives first. Note that `autoupdate` cannot
compute a new checksum on its own; if a user updates before the workflow has
pushed the manifest, Scoop will reject the download and they should re-run
`scoop update` once the bucket catches up. The workflow pushing real hashes on
every release is what keeps that window empty.

## Not in scoop-extras or the main bucket

Those buckets require a maintainer of their own to adopt the manifest. A
first-party bucket is the normal route for a desktop app of this size.
